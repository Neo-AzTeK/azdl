# DLC delivery contract

## Supported today

Provider manifests with encrypted filenames use the depot key to validate paths and staged files. Depot and revision IDs, the encrypted payload CRC, and any filename hashes are checked; symbolic links, malformed names, and invalid keys are rejected. The optional `live_staged_dlc_matches_selected_manifest` check accepts `AZDL_LIVE_DLC_DEPOT_KEY` for encrypted snapshots.

For a saved base-game snapshot, `live_base_provider_matches_windows_manifest` accepts `AZDL_LIVE_BASE_APP_ID`, `AZDL_LIVE_BASE_APPINFO`, and `AZDL_LIVE_BASE_MANIFEST_DIR`. It checks the same depot-selection and manifest-validation path without downloading game files. On 2026-10-26, Moon Sweepers App ID 5335510 passed against its then-current public appinfo and provider manifest. This is not a Windows installation or launch test.

Paused catalog archive transfers can be resumed from the game page or transfer drawer. The launcher validates the transfer's game and DLC staging directory, then registers a background DLC task so launch and other content mutations remain guarded while it resumes. User-requested pauses and cancellations do not generate failure notifications; cleanup failures remain visible. Depot DLC transfers cannot be paused and are retried from the game page after interruption.

The launcher installs source supplied HTTPS DLC archives and has an experimental Steam depot DLC path for managed `steamidra` base installs. Archive downloads check any supplied SHA-256 digest. Both paths stage files and reject archive path traversal and symlinks. Steam depot DLC adds files or reuses identical existing files. Explicit archive DLC can also replace a base file after saving a verified backup in its transaction journal; removal or interrupted-install recovery restores that file, including after a game move. Another DLC can share identical overlay bytes with its own verified copy of the base backup, so either removal order preserves the remaining owner and the last removal restores the base. Different-content DLC-on-DLC overlays remain unsupported. A per-DLC manifest records owned files and hashes for safe removal. Recovery refuses to remove files changed after installation began. Archive DLC holds the game content lock from download through commit and removes its temporary archive and job records after success, failure, or cancellation; Resume completes a paused archive transfer and commits the DLC under the same game lock. Failed depot downloads retain isolated group staging. Success and cancellation remove it, and clearing a stopped job discards its validated owned staging. Retry validates saved depot IDs, manifest revisions and manifest SHA-256 values before reuse; changed revisions discard old groups. The bundled Windows engine verifies existing chunks against their manifest SHA-1 before skipping downloads; Linux plugin engines retain their own resume behavior. Verified download payloads move through transaction and installation staging on the same filesystem, with durable copying across filesystems. The DLC ownership and rollback journal remains intact. New native tests cover retry, move fallback, chunk checks and tail preservation; execution and live interruption acceptance remain pending in GitHub Actions.

Steam Store DLC metadata is descriptive and is not a download source. Catalog DLC is enabled only when its source supplies a valid HTTPS archive artifact and does not explicitly mark the entry unavailable. The game page disables a Steam depot DLC install for an explicit wrong parent, no depot matching the Windows/English target, or a required depot without a public manifest. Missing parent identity and empty depot metadata remain checkable unknown states with a short explanation. A known incompatible base revision also disables a new download, while an existing DLC observation can still be rechecked without changing files. The pre-download base check now requires the receipt to cover exactly the current Windows/English base depots, including exact revisions resolved through shared-app references. For an old base without a receipt, the read-only verifier resolves required shared depots through their manifest-owning App IDs and checks installed bytes before recording a verified revision. An offline fixture covers a parent and shared depot, including changed-file rejection; live shared-base acceptance remains open. Fresh steamidra base installs exclude catalog DLC archives, resolve shared depots, and publish a complete verified base from isolated content App ID groups. Their temporary provider bundles, downloaded add-ons, and depot groups use a per-game scratch directory that is cleared after terminal outcomes and before a retry. A failed base receipt write rolls back the new directory only if it still matches the verified manifests, and records the transfer as failed. For Steam depot DLC, the installer resolves exact matching provider manifests for the selected DLC. Selected base and DLC manifests are checked before download for conflicting content, Windows case collisions, and file-as-directory paths. After download, the staged payload must match every selected manifest by size and SHA-1; unlisted files, symlinks, and conflicting depot paths are rejected before commit. An old install can check whether every DLC file already matches the manifest; azdl records that observation without claiming ownership or offering removal. If DLC files are missing, azdl verifies every required base depot file before recording a legacy base revision and proceeding with the download. A changed or incomplete base requires reinstalling the base game. Identical files shared by the base game or another DLC are reused with ownership tracking; different-content conflicts are reported rather than overwritten.

The researched evolution plan is in [DLC_PLAN.md](DLC_PLAN.md). The Steam depot path reuses depotkit and the archive DLC transaction. A Linux check copied a real base game without its DLC, then verified the old base, downloaded and committed the DLC, checked the installed hash, and removed the DLC without changing base files. In-game access, Windows behavior, and ordered Steam depot overlays still need acceptance and implementation work. The generic provider session ABI below is a separate extension.

Catalog DLC search results open the parent game's existing page. The selected DLC ID is included in that page's DLC lookup even when the parent metadata omits it; after a base install, the game is matched by Steam App ID and the selected row is brought into view. Numeric App ID search now falls back to public appinfo when a DLC has no Store page or the Store request fails; appinfo must still provide a name and parent identity for the existing route. This route has offline ID, unlisted-DLC lookup, and frontend bridge tests, without a live UI acceptance run. An offline lifecycle test verifies that content staged in two separate download groups can be merged, committed as one managed DLC, and removed without changing the base game. A second offline test drives the production group loop with a controlled downloader, checking the distinct content App IDs, exact staged manifests, cumulative progress, commit, and removal. Native multi-App downloading and in-game access remain unverified.

The desktop serializes game launch with DLC task registration and file mutations. It refuses to launch while a DLC task is active and refuses install, removal, or recovery while that game is running. The Steam depot worker now registers its transfer job before metadata and base-file checks, so early errors and cancellation have a persisted terminal status. The native depot downloader is loaded only from an installed plugin declaring depot download capability (`steam_depot_download`), defaulting to `steamidra`; an undeclared plugin cannot supply it. On Windows, after validating the installed selected plugin, azdl uses its own pinned Qt-free depotkit.dll beside the executable. The Windows Qt plugin wrapper does not export depotkit_download and cannot provide this transport. Release installers and portable archives include the engine and license notices. CI/release includes a Windows load/export/invalid-request smoke test, not a live game download test. Manifest bundle download URLs are resolved dynamically through the plugin's declared `catalogUrl` or `downloadUrl` rather than a hardcoded endpoint. If that plugin or downloader is removed, the existing DLC rows remain visible but install and file-check actions are disabled with a reason; removal and recovery remain available. This covers games launched and tracked by the desktop; processes started outside azdl are not yet identified.

On Windows, job liveness checks now query the recorded process handle. A download left in `Running` by a crashed launcher can be shown as interrupted, and a stale ordinary download lock can be reclaimed on retry. This has a Windows compile check; runtime restart behavior still needs Windows acceptance.

The native depot progress callback serializes access to its shared Rust state before recording cumulative bytes. The first callback immediately records progress and checks cancellation; subsequent callbacks are throttled. It releases the lock before requesting native cancellation, so callbacks from separate workers cannot create aliased mutable Rust references or block each other while cancellation is dispatched. Offline fixtures check concurrent progress and the native callback/control ABI; live cancellation still needs acceptance.

An interrupted DLC journal must be recovered before another DLC is installed or an unrelated DLC is removed. The backend enforces this under the game lock, and the game page disables those actions while leaving Recover available. A lifecycle fixture verifies that recovery preserves a separate installed DLC and that its removal works afterward.

A game move now checks for a live DLC download while holding the game content lock. The desktop also coordinates move and DLC task registration under that lock, so either operation blocks the other before its worker starts. An offline move fixture verifies that a live DLC job leaves the source game in place and that the move succeeds after the worker ends.

Desktop game uninstallation checks registered DLC and move tasks inside the same game content lock used for removal. A task registered first blocks uninstall; an uninstall that gets the lock first completes before a DLC task can register. The existing core live-job check also blocks removal while a DLC worker is active. An offline desktop fixture verifies both registered-task cases leave the game intact.

Immediately before a staged Steam DLC is committed, azdl reacquires the game content lock, compares the current base receipt with the revision pinned before download, and checks every required base depot file against its exact provider manifest. The transition to file commit happens under that same lock. A changed or missing receipt or changed base file aborts without installing DLC files; an offline grouped-DLC fixture covers both rejection paths and success. Concurrent external writers are outside the lock's control.

For a shared Steam depot, the DLC resolver follows `depotfromapp` when the current app has no public manifest, rejects cycles, and selects an exact provider artifact from the app that supplies the manifest. Downloads are grouped by their resolved content App ID into separate staging directories, then verified and merged before commit. The transfer shows cumulative progress across groups, with the selected manifests' file sizes as an estimated total. This route is covered by offline fixtures; a live shared-depot download has not yet been accepted.

The optional `tests/live_dlc_manifest.rs` check verifies an external staged snapshot with `AZDL_LIVE_DLC_MANIFEST`, `AZDL_LIVE_DLC_STAGING`, `AZDL_LIVE_DLC_DEPOT_ID`, and `AZDL_LIVE_DLC_MANIFEST_ID`; run it with `cargo test --test live_dlc_manifest -- --ignored`. On 2026-10-16, the exact provider manifest for depot `3875100`, revision `5309998554743987160`, matched an isolated copy of the real 539,727,136 byte DLC file. This checks staged content and path safety, not a new CDN download or in-game access.

The optional `tests/live_dlc_install.rs` check uses `AZDL_LIVE_DLC_LIBRARY_DIR`, `AZDL_LIVE_DLC_DATA_DIR`, `AZDL_LIVE_DLC_GAME_ID`, and `AZDL_LIVE_DLC_APP_ID`. Its data directory must contain a copied base game under `games/live-dlc-acceptance` and the installed provider under `plugins/steamidra`. Run it with `cargo test --test live_dlc_install -- --ignored`; it downloads DLC, installs managed files, removes them, and compares the copied base file names and sizes. On 2026-10-16, this passed on Linux for DLC `3875100` through the current grouped staging path. It does not establish in-game access or multi-App shared-depot behavior.

## Provider-owned delivery

Windows DLC finalization closes the synced manifest before renaming its transaction directory. Base backups are copied and synced through a writable handle; syncing a read-only handle can fail with access denied on Windows. Finalization write failures include the operation and destination path. Archive-free regression tests cover staged installation, manifest relocation, removal, and backup writes; the Windows release workflow runs DLC tests before packaging. Native validation of this change remains pending.

Arachnel API 4 exposes a JSON catalog boundary, but its C ABI does not expose the C++ `startOwnedDownload` method. Rust must not call C++ virtual methods or infer a depot URL from a Store DLC ID. A future provider-owned DLC adapter should use a versioned C ABI with an opaque session handle:

1. The host passes the source game ID, DLC ID, platform, and an isolated staging directory. The plugin may download into that directory and report progress and cancellation through the adapter. It receives no writable base game path.
2. The plugin returns a manifest of staged files with relative paths and hashes. The host checks IDs, file types, symlinks, traversal, collisions with base files, and hashes before committing any file.
3. The host commits through the same DLC file manifest and lock used for explicit archives. Cancellation, failure, and process death leave a recoverable state. Removal deletes only unchanged files owned by that DLC.
4. The adapter advertises its ABI version and `owned_dlc` capability. Plugins without it remain compatible and their provider-owned DLC stays unavailable in the UI.

The implementation gate is a real API 4 provider package on both Linux and Windows, with a live install, interruption, removal, and game move test. Until that gate passes, the UI must never present provider-owned DLC as downloadable.
